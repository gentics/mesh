Overview

Was dieser Server ist – und was nicht.

Der Mesh MCP Server stellt sechs read-only Werkzeuge für Gentics Mesh CMS zur Verfügung, die ein Large Language Model über das Model Context Protocol direkt aufrufen kann. Er ersetzt keine Mesh-Funktion; er ist die kontrollierte Brücke, über die AI-Systeme strukturierten Content abfragen, ohne dass ein Sprachmodell direkten Zugang zur Mesh-API erhält.

Read-only by default

Sämtliche Mutationen (Mesh-REST-PUT/POST/DELETE und GraphQL mutation) sind hart blockiert. Aktivierbar nur über bewusstes Setzen von MESH_READ_ONLY=false – nicht empfohlen für Produktion.

Defence-in-Depth Policy-Layer

Projekt-, Schema- und Sprach-Allowlists werden vor jedem Mesh-Call geprüft. Selbst wenn ein Tool durch ein LLM falsch parametrisiert wird, sieht Mesh die Anfrage nie.

GraphQL mit Guardrails

Read-only Queries: Mutation-Keyword im Body führt zu FORBIDDEN. Verschachtelungstiefe per Brace-Counting begrenzt (MESH_GRAPHQL_MAX_DEPTH, Default 6).

Zwei Transports, eine Surface

Stdio und HTTP teilen sich denselben ToolDispatcher – das LLM sieht in beiden Modi identische Tool-Namen, Inputs und Outputs.

Production-grade Auth

Constant-time Bearer-Token-Vergleich über MessageDigest.isEqual. Erweiterbar über die AuthValidator-Schnittstelle für OAuth 2.1 / JWT.

Operability eingebaut

/healthz, /readyz und /metrics im Prometheus-Textformat. Deployment über das Mesh-Helm-Chart (Sub-Chart), Docker-Multi-Stage-Build mit Non-Root-User.

Komposition

Main validiert die ENV-Konfiguration über MeshConfig.load(), instanziert den MeshClient und entscheidet anhand MCP_TRANSPORT bzw. CLI-Flags, ob ein McpServerRunner (stdio) oder ein HttpMcpServer gestartet wird.

Beide Transport-Implementierungen besitzen denselben ToolDispatcher, der die sechs Use-Case-Klassen kennt und die korrekte Methode mit aus dem JSON-RPC-Request extrahierten Argumenten aufruft.

PolicyService wird aus jedem Use-Case vor dem Mesh-Call angesprochen – das ist die zentrale Fail-Fast-Stelle für Allowlist-Verstöße.

Designprinzip: Tools haben keinen Zugriff auf den HTTP-Exchange. Das verhindert, dass ein Tool versehentlich Request-Header oder Antwort-Status manipuliert.

Tool API

Sechs Tools, alle read-only.

Tool-Namen, Input-Schemas und Output-Formate sind über beide Transports identisch und versioniert. Schema-Änderungen sind Breaking-Changes und schlagen sich in einem Minor-Bump nieder.

Listet alle erlaubten und erreichbaren Gentics-Mesh-Projekte.

{}

    { "name": "demo", "uuid": "abc123…" },

Listet Schemas eines erlaubten Projekts mit allen Felddefinitionen.

// Input

Input-Schema · Optionen

  "uuid": "f3b6…-c7a1",
  "language": "de",                  // optional, Default "de"

Volltextsuche über Nodes eines Projekts. Benötigt eine konfigurierte Elasticsearch-Instanz auf Mesh-Seite.

Input-Schema · Defaults 
{

  "query": "Delorean",
  "schema": "vehicle",               // optional
  "language": "de",                  // Default "de"
  "fields": ["title","teaser","body"], // Default ["title","teaser","body"]

  "language": "de"                   // optional, Default "de"
}

Führt eine read-only GraphQL-Query gegen ein erlaubtes Projekt aus. Mutations werden blockiert, Depth wird gegen MESH_GRAPHQL_MAX_DEPTH geprüft.

Mesh Protection

Rate-Limit · Bulkhead · Circuit Breaker.

Damit ein LLM mit einer Retry-Schleife oder ein generell sehr fragefreudiger Agent Mesh nicht in die Knie zwingt, sitzt der MeshCallGuard zwischen jedem Tool-Call und der Mesh-Anbindung. Drei unabhängige Layer, alle Fail-Fast.

1 · Token-Bucket Rate-Limit

Pro Bearer-Token und global. Token-Cost spiegelt grobe Mesh-Last wider: list_projects=1, list_schemas=1, get_node=2, get_webroot=2, search_nodes=3, run_graphql=5. Stdio-Modus ist vom Per-Token-Limit ausgenommen (es gibt nur einen Client).

Default: 20/s pro Token, 50/s global. Bei Überschreitung: RATE_LIMITED → HTTP 429 + Retry-After: 1.

2 · Bulkhead (Concurrency Cap)

Begrenzt parallele in-flight Mesh-Calls. Wichtig, weil ein einzelnes mesh_run_graphql 5 Sekunden binden kann – das ist kein Rate-, sondern ein Concurrency-Problem.

Default: 10 gleichzeitige Calls. Bei Überschreitung: BUSY → HTTP 429 + Retry-After: 1.

3 · Circuit Breaker

Wenn Mesh anfängt zu erroren, hört der Server auf, Last zu produzieren — statt blind nachzulegen. Sliding-Window über die letzten N Calls; Client-Faults (Validation, Forbidden, NotFound) zählen nicht, nur echte Mesh-Probleme.

Default: 50 % Failure-Rate über 20-Call-Fenster → öffnet für 30 s. Bei offenem Breaker: CIRCUIT_OPEN → HTTP 503 + Retry-After: 30.

Tuning-Tabelle

VariableDefaultWann erhöhen / senken
MCP_RATE_LIMIT_PER_SECOND50Erhöhen, wenn viele Tokens echte Last erzeugen sollen.
MCP_RATE_LIMIT_PER_TOKEN_PER_SECOND20Senken, um einzelne Agents stärker zu drosseln.
MCP_MESH_MAX_CONCURRENT10Spiegelt die Mesh-Capacity. Faustregel: 1–2× CPU-Kerne von Mesh.
MCP_CIRCUIT_BREAKER_ENABLEDtrueIn Lasttests evtl. false, sonst immer an.
MCP_CIRCUIT_BREAKER_FAILURE_RATE_PERCENT50Niedriger = empfindlicher Breaker.
MCP_CIRCUIT_BREAKER_WINDOW_SIZE20Größer = stabiler, träger.
MCP_CIRCUIT_BREAKER_OPEN_DURATION_MS30000So lang braucht Mesh zum Atmen.
MCP_GRAPHQL_MAX_QUERY_LENGTH4000Erhöhen für Power-User-Queries; Senken, wenn LLMs zu lange Queries bauen.

Erwartetes Client-Verhalten

Bei HTTP 429 oder 503 sollte ein guter Client den Retry-After-Header lesen und exponentiell zurückwarten. LLM-Frameworks (OpenAI Agents SDK, LangChain) machen das ootb; eigene Integrationen müssen es selbst implementieren.

Innerhalb der MCP-Antwort kommt zusätzlich der JSON-RPC-Envelope mit result.isError = true und einem strukturierten Error-Body – so kann das LLM den Grund sprachlich verarbeiten ("Tool ist gerade ausgelastet, frag in einer Minute nochmal").

Transports

stdio für lokal, HTTP für alles andere.

Stdio bleibt der natürliche Kanal für Claude Desktop und vergleichbare Child-Prozess-Clients. HTTP ist die Wahl für Remote-Anbindungen an OpenAI Agents, LangChain, n8n, Open WebUI oder eigene LLM-Stacks im Cluster.

stdio

Lokale Child-Prozess-Clients

  • JSON-RPC über stdin / stdout
  • Genau ein Client pro Prozess (sessionsgebunden)
  • Auth über Prozess-Spawning impliziert
  • Aktivierung: kein MCP_TRANSPORT setzen, oder --stdio
  • Beispiel-Clients: Claude Desktop, Cursor, Continue, Zed
HTTP · Remote

Remote-MCP für LLM-Stacks

  • JSON-RPC 2.0 über POST /mcp
  • Mehrere parallele Sessions auf Virtual-Thread-Executor
  • Bearer-Token-Auth (constant-time)
  • Aktivierung: MCP_TRANSPORT=http oder --http
  • Beispiel-Clients: OpenAI Agents, LangChain, n8n, Open WebUI, vLLM-Stacks

Streamable HTTP: aktuell Request/Response über POST /mcp. Server-initiierte SSE-Streams (für Progress-Events) sind als Folge-Iteration geplant. Für alle Tool-Calls in diesem Server reicht das aktuelle Request/Response-Modell aus.
Authentication

Bearer heute, OAuth morgen.

Aktuell setzt der Server auf einen statischen Bearer-Token, der per ENV gesetzt und konstant-zeitlich verglichen wird. Der AuthValidator-Hook ist die Erweiterungsstelle für OAuth 2.1 und JWT-Introspection.

BearerTokenValidator

Akzeptiert Authorization: Bearer <token>. Vergleich über MessageDigest.isEqual, sodass keine Timing-Seitenkanäle den Token leaken.

javaAuthValidator v = new BearerTokenValidator(token);
boolean ok = v.isAuthorized(header);

Eigene Auth-Implementierung

Implementiere AuthValidator und reiche sie aus Main in den HttpMcpServer – fertig.

javaAuthValidator v = header -> {
    // JWT introspection / OAuth resource-server validation
    return MyJwt.verify(header);
};

Auth deaktivieren (nur hinter Reverse-Proxy)

shellMCP_TRANSPORT=http MCP_AUTH_DISABLED=true java -jar target/mesh-mcp-server.jar
Achtung: Bei MCP_AUTH_DISABLED=true nimmt jeder, der den Port erreicht, Tool-Aufrufe vor. Nur in Setups einsetzen, in denen NGINX/Ingress die Auth bereits terminiert.
Operational Endpoints

Health, Readiness, Metriken.

Diese Endpoints stehen ohne Auth-Prüfung zur Verfügung und sind dafür gedacht, vom Cluster (Kubernetes Probes, Prometheus-Scraper) konsumiert zu werden.

GET /healthz Liveness: 200 OK, solange der Prozess läuft.
GET /readyz Readiness: 200 OK, sobald der HTTP-Server gebunden ist.
GET /metrics Prometheus-Textformat: HTTP-Requests, Auth-Failures, Tool-Counts / -Errors / -Duration, Uptime.
POST /mcp JSON-RPC 2.0 MCP-Endpoint. Auth erforderlich.

Error Codes

Stabile Codes für Monitoring und LLM-Handling.

Jeder Tool-Fehler wird als AppError mit einer der unten gelisteten Codes serialisiert. Neue Codes werden unten angehängt; existierende Codes werden nie umbenannt.

VALIDATION_ERROR
HTTP 400
Ungültiger Input oder Startup-Mis-Configuration. Pflichtfelder fehlen, Typen passen nicht.
FORBIDDEN
HTTP 403
Policy-Verstoß: Projekt/Schema/Sprache nicht in der Allowlist. Read-only-Modus aktiv und Schreibversuch.
NOT_FOUND
HTTP 404
Node / Webroot-Pfad existiert nicht im Mesh-Projekt.
UPSTREAM_ERROR
HTTP 502
Gentics-Mesh-Aufruf scheitert (Timeout, Connection-Refused, 5xx von Mesh).
INTERNAL_ERROR
HTTP 500
Unerwartete Exception im Server. Sollte in Logs auftauchen und einen Bug-Report wert sein.
RATE_LIMITED
HTTP 429
Token-Bucket leer (global oder pro Bearer-Token). Antwort enthält Retry-After.
BUSY
HTTP 429
Bulkhead voll – zu viele parallele Mesh-Calls. Antwort enthält Retry-After.
CIRCUIT_OPEN
HTTP 503
Mesh ist gerade unhealthy; Breaker fängt Last ab. Antwort enthält Retry-After = Cooldown-Restzeit.

JSON-Format eines Fehlers

json{
  "error": {
    "code": "FORBIDDEN",
    "message": "Projekt 'staging' ist nicht in der Allowlist. Erlaubt: [demo, shop]"
  }
}
Deployment

Mesh-Helm-Chart, Docker, Jenkins.

Seit dem Umzug nach mesh-enterprise wird der MCP-Server als Sub-Chart vom Helm-Chart von Mesh deployt. Ein eigenes Chart existiert nicht mehr. Image-Build und Versionierung folgen dem Mesh-Release.

Container-Image

Image-Name: repo.gentics.com/mesh/mcp-server. Tag entspricht der Mesh-Version (vom mesh-enterprise-Parent-POM geerbt). Image wird durch die mesh-enterprise-Jenkins-Pipeline gebaut und gepusht. 

shell# Lokaler Smoke-Build (Standalone, ohne Reactor):
VERSION=$(mvn -q help:evaluate -Dexpression=project.version -DforceStdout)
docker build --build-arg VERSION="$VERSION" -t mesh-mcp-server:dev .

docker run -i --rm \
  -e MESH_BASE_URL=http://mesh:8080 \
  -e MESH_USERNAME=admin \
  -e MESH_PASSWORD=admin \
  -e MESH_ALLOWED_PROJECTS=demo \
  mesh-mcp-server:dev

Helm (über Mesh-Chart)

Werte für den MCP-Server liegen im Mesh-Chart unter dem mcpServer:-Key (siehe helm-chart/values.yaml im mesh-enterprise-Repo, Section "Gentics Mesh MCP Server"). Aktivierung: 

yaml · mesh-values.yamlmcpServer:
  enabled: true
  image:
    repository: repo.gentics.com/mesh/mcp-server
    pullSecret: docker-gentics-com
  transport:
    mode: http
    auth:
      token: "$(openssl rand -base64 32)"
      # alternativ: existingSecret: mcp-auth   (Key: MCP_AUTH_TOKEN)
    cors:
      origins:
        - https://chat.example.com
  mesh:
    username: "admin"
    password: "YOURPW"          # in Prod via existingSecret
    # existingSecret: mesh-admin-credentials
    allowedProjects: "demo"
    allowedLanguages: "de,en"
    readOnly: true
  protection:
    rateLimit:
      globalPerSecond: 50
      perTokenPerSecond: 20
    maxConcurrent: 10
    circuitBreaker:
      enabled: true
  ingress:
    enabled: true
    hosts:
      - host: mesh-mcp.example.com
        paths: ["/"]

Der Chart erzeugt dann ein Deployment <release>-mcp-server, einen Service (im HTTP-Modus), optional einen Ingress sowie zwei Secrets (<release>-mcp-server-mesh mit Mesh-Credentials, <release>-mcp-server-auth mit Bearer-Token). Beide Secrets können über existingSecret-Verweise extern gepflegt werden.

Kubernetes – Probes

Stdio: Liveness über pgrep. HTTP: httpGet auf /healthz bzw. /readyz.

CI & Release

Der Server folgt der Mesh-Release-Kadenz. Push auf main oder einen release/*-Branch löst im Jenkins von mesh-enterprise folgenden Workflow aus:

  1. mvn -B -ntp -pl mcp-server -am verify
  2. Effektive Modul-Version aus dem POM ableiten (geerbt vom Parent)
  3. Docker-Build mit --build-arg VERSION=<mesh-version>
  4. Push nach repo.gentics.com/mesh/mcp-server:<mesh-version> (Credentials gentics-registry)
